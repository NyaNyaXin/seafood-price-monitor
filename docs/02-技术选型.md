# 沈阳市冻品水产行情系统 — 技术选型

> 版本 v2.0 · 2026-11-23 · 配套《01-需求文档》
>
> **v2 技术变更**：新增 `GetPriceList` 采集链路（品种分规格 + 30 天历史），数据库从 1 张数据表扩到 3 张（`price_obs` 市场快照 / `spec_snapshot` 分规格 / `product_trend` 30天趋势）。看板曲线改为品种维度双线（全国/辽宁），新增全国规格栏目。全部冻品过滤。下文 v1 的"只有当日快照/曲线键三元组画图"等技术细节已被 v2 实现取代，其余选型（SQLite/Python/静态HTML/ECharts CDN/cron）不变。
>
> **v2.1 前端重构**：单页看板拆为 4 个静态页（`index.html` / `trend.html` / `specs.html` / `history.html`），共用 `assets/style.css` 与 `assets/common.js`。公共层只解析一次 `data.js`，构建 `window.TIDE`（obs / seriesMap / trends / specs / 工具函数），各页脚本只做本页渲染。新增 `data/data.js` 的 `meta.catalog` 字段（29 个重点品种 ID→名称），供规格页计算并展示覆盖率。ECharts 只在走势页加载。
>
> **v3 标准化**：前端从静态 HTML 迁移到 **Nuxt 4** 标准项目——`app/` 目录（文件路由 `app/pages/`、组件自动导入、composable 数据层），交互控件用 **Reka UI**（`reka-ui/nuxt` 官方 module，Select / Tabs，无样式组件 + 自写 CSS），ECharts 改为 npm 依赖（弃用 CDN）。`ssr:false` 纯客户端渲染，数据从 `public/data.json` 读取（采集脚本写出，`no-store` 破缓存）。Python 采集 / SQLite / cron 链路不变。旧静态页已在迁移验证完成后清理（备份另存于项目上级目录 zip）。Node.js 要求 22+。
>
> **v4 数据层**：真相源从 SQLite 迁到本机 **PostgreSQL**（`seafood_price` @ `127.0.0.1:5432`，本机 trust 空密码）。`db.py` 改为双后端：`config.DB_BACKEND` 切 `postgres` / `sqlite`，**业务 SQL 一行未改**，由适配层 `_to_pg()` 把 `?`→`%s`、`:name`→`%(name)s`，并用自定义 `Row` 兼容 `sqlite3.Row` 的 `row[0]` / `row['col']` / 切片语义。价格列必须用 `DOUBLE PRECISION`：PG 的 `REAL` 是 float4，会把 `40.67` 截成 `40.669998`；`NUMERIC` 则回 `Decimal`，会让 `json.dumps` 直接报错。迁移由 `migrate_to_pg.py` 完成：建库 → 建表建索引 → 全量搬数据（保留原 id）→ `setval` 推进 SERIAL 序列 → 逐行 + 聚合双重校验，幂等可重复执行。SQLite 文件转为历史归档，不再写入。
>
> **v5 取数链路重构**：取消 `public/data.json` 中间层。新增 Nitro 接口 `server/api/price-data.get.ts`，用 **`pg` 连接池**（`server/utils/pg.ts`）直查 PostgreSQL，冻品过滤下推到 SQL（`LIKE ANY(ARRAY[...])`），返回 `meta / observations / spec_snapshot / trends` 四段结构，口径与 Python 侧 `db.all_observations / all_spec_snapshot / all_trends` 逐条对齐（已实测比对一致）。`app/composables/usePriceData.ts` 改读 `/api/price-data`，删除了 `data/data.js` 与 `public/data.json`。参考数据（品种清单/市场/冻品判定关键词/阈值）抽到 `shared/reference.json`，Python `config.py` 与 Node 服务端共读，消除前后端双份定义。采集调度从 WSL cron 改为 **Windows 任务计划程序**（WSL2 回环与本机 PG 不互通），线上走 `deploy/systemd/*`。数据库连接统一为 `DB_*` 环境变量（Python 与 Node 共用）。`pnpm generate` 不再适用——必须有 Node 进程。
>
> **v6 数据源扩容**：市场范围从沈阳 2 家扩到全国 59 家（`GetPriceNow` 改 `rid=0` + `pageSize=500`，3 页拉完约 1047 条）。`shared/reference.json` 的 `markets` 升级为 `{ id: { name, tier } }`，`tier` 分 `core`（沈阳）/ `province`（辽宁其他）/ `national`（全国参考）。表结构未变；冻品日采集量 15 → 120 条。
>
> **v7 去 SQLite + 手动采集（当前版本）**：SQLite 后端**彻底移除** —— `db.py` 只留 PostgreSQL（psycopg2 + `RealDictCursor`，SQL 直接写 `%s` / `%(name)s`，删掉 `_to_pg()` 适配层、`Row` 兼容类与 `DB_BACKEND` 开关）。建库建表改由 **`scripts/init_pg.py`** 承担：幂等，`--seed` 导 `scripts/seed/*.json` 种子、`--dump-seed` 反向导出、`--recreate --yes` 重建、`--dry-run` 只打印不连库；`migrate_to_pg.py` 删除，`data/prices.db` 归档到 `data/archive/`。采集改为**本机手动执行**，不再挂 Windows 任务计划（线上 Docker `fetch` 容器仍保留每日循环）。同时修掉 `parse_md_date` 年份推断缺陷：无年份日期改为「晚于抓取日则回退一年」，并清掉 52 条 trend + 2 条 spec 未来日期脏数据（备份 `data/archive/future-dates-2026-11-24.json`）。
>
> **v4.1 目录整理**：Python 脚本从项目根目录集中到 `scripts/`（`config.py` / `db.py` / `fetch.py` / `migrate_to_pg.py`），根目录只保留前端、部署与文档文件。关键改动：`config.ROOT` 由 `Path(__file__).parent` 改为 `Path(__file__).parent.parent`；`fetch.py` / `migrate_to_pg.py` 启动时执行 `sys.path.insert(0, 脚本目录)`，可从任意工作目录调用。
>
> **部署注意**：本机 PG 只监听 `127.0.0.1` / `::1`（Windows 回环），WSL2 的 `127.0.0.1` 与其不互通，**WSL 内跑 cron 会连不上 PG**。建议采集改在 Windows 侧（任务计划）执行；或改 `listen_addresses` + `pg_hba.conf` 放行 WSL 网段，并用 `networkingMode=mirrored` 规避 WSL2 IP 漂移。

## 0. 一句话结论

**本地 SQLite 存储 + Python 定时抓取 + 单页 HTML/ECharts 看板**，v1 零成本、纯本地、不锁死；将来若要多端在线看，再平滑接 WorkBuddy 云服务（云数据库 + 发布为应用）。

## 2. 整体架构

```
   [水产时价云接口]  znyj.nftec.agri.cn:8089
            │  GET /API/Product/GetPriceNow + GetPriceList (免登录, rid=4)
            ▼
   ┌─────────────────────┐
   │ 采集脚本 (Python)    │  ← Windows 计划任务 / Linux systemd timer，每天 07:00
   │  1. 分页拉全量       │
   │  2. 过滤 537/538     │
   │  3. 清洗(去0/补年份) │
   │  4. 幂等入库         │
   └──────────┬──────────┘
              ▼
   ┌─────────────────────┐
   │ PostgreSQL           │  ← 唯一真相源，逐日累积
   │  price_obs / spec_snapshot
   │  product_trend / fetch_log
   └──────────┬──────────┘
              ▼  pg 连接池（Nitro 服务端直查）
   ┌─────────────────────┐
   │ GET /api/price-data  │  ← 冻品过滤下推 SQL
   └──────────┬──────────┘
              ▼
   ┌─────────────────────┐
   │ Nuxt 4 四页看板       │  ← ECharts 曲线 + 涨跌表
   └─────────────────────┘
```

**关键设计**：PostgreSQL 是唯一真相源；服务端（Nitro）直查数据库，**不再生成 JSON 中间文件**。采集、存储、展示三层解耦，任何一层可单独替换。

## 3. 分层选型对比

### 3.1 抓取调度

| 方案 | 优点 | 缺点 | 结论 |
|---|---|---|---|
| **Python + 系统定时任务** | 零依赖、可控、易调试 | 依赖本机开机 | ✅ 推荐 |
| GitHub Actions cron | 免运维、云端跑 | 国内站访问不稳、有延迟、免费额度限制 | ⚠️ 备选 |
| 常驻服务（APScheduler） | 灵活 | 需常驻进程，重 | ❌ 杀鸡用牛刀 |

**推荐**：Python `requests`（或标准库 `urllib`）写采集脚本 + 系统定时。
- Windows：任务计划程序（`schtasks`）
- WSL/Linux：cron
- 脚本内置重试（3 次，指数退避）和日志。

### 3.2 存储

> 以下为 v1 选型当时的对比记录，保留作决策留档。实际演进：v4 已换成 **PostgreSQL** 作真相源，v7 移除 SQLite 后端（见文首变更）。

| 方案 | 优点 | 缺点 | 结论 |
|---|---|---|---|
| **SQLite** | 单文件、零配置、Python 内置 `sqlite3`、够用 10 年 | 单机，不能直接给网页读 | ✅ 推荐（真相源） |
| CSV/JSON 文件 | 最简单、人可读 | 无约束、查询弱、易写坏 | ⚠️ 仅作导出备份 |
| WorkBuddy 云数据库 | 在线可访问、免运维 | 需发布应用、前端 SDK 接入、当前需求用不到 | ⚠️ 将来扩展 |
| PostgreSQL/MySQL | 强大 | 远超需求，需部署维护 | ❌ 过度设计 |

**推荐**：SQLite 做真相源，定期导出 CSV 备份。理由：数据量小、零运维、幂等约束好实现、跨年/补抓都容易处理。

### 3.3 看板前端

| 方案 | 优点 | 缺点 | 结论 |
|---|---|---|---|
| **单页 HTML + ECharts** | 图表强（折线/涨跌）、中文文档全、单文件、可本地打开 | 需读导出数据 | ✅ 推荐 |
| Chart.js | 轻量 | 金融类图表/交互弱于 ECharts | ⚠️ 备选 |
| Vue/React 工程 | 组件化 | 数据规模小，引入构建链不值 | ❌ 过度 |

**推荐**：ECharts（CDN 或本地引入）。折线图、dataZoom、tooltip、涨跌标记开箱即用。页面数据由 `/api/price-data` 提供（v5；v1 的 `data.json` 直读方案已废弃）。

### 3.4 在线化（可选，将来）

| 方案 | 成本 | 说明 |
|---|---|---|
| WorkBuddy 云服务 + 发布为应用 | 免费额度内 | 云数据库存历史 + 静态发布，得到在线链接、手机可看 |
| 自建服务器 + Nginx | 需服务器 | 完全自主，需运维 |

**建议**：v1 纯本地跑通；确需在线看时，用 WorkBuddy 官方链路（cloud-service 托管 + sites 发布），不引入自建服务器。届时需评估云服务配额/计费。

## 5. 关键实现要点

### 5.1 采集脚本（fetch.py）伪代码

```python
BASE = "http://znyj.nftec.agri.cn:8089"
TOKEN = "0000000000000000"
# v6 起：市场白名单在 shared/reference.json（59 个，tier 分层），采集端读它
MARKETS = {537: "辽宁省沈阳水产品批发市场", 538: "辽宁省前当堡鲜鱼批发市场"}  # 核心两家

# 1. 分页拉全国(rid=0, pageSize=500，全国 1047 条约 3 页)
page = 1
while True:
    r = GET f"{BASE}/API/Product/GetPriceNow"
         params={token, rid=4, PageNum=page, pageSize=100}
    items += r.Data.Items
    if page >= r.Data.TotalPageCount: break
    page += 1

# 2. 过滤 + 清洗
for it in items:
    if it.unit_id not in MARKETS: continue
    price = float(it.value)
    if price <= 0: continue              # 去缺报占位
    obs_date = parse_cn_date(it.date, fetch_date)  # "11月23日" -> "2026-11-23"

# 3. 幂等入库
INSERT ... ON CONFLICT(obs_date, market_id, product_id, spec_id) DO UPDATE

# 4. 写 fetch_log（v5 起不再导出前端 JSON，看板由服务端直查）
```

### 5.2 前端读数据（历史方案，已被 v5 取代）

浏览器直接 `file://` 打开 HTML 时，`fetch('data.json')` 会被 CORS 拦截。v1 的两种解法：

| 方案 | 做法 | 适用 |
|---|---|---|
| A. 内联数据（v1 采用） | 采集脚本生成 `data.js`（`window.PRICE_DATA={...}`），HTML 用 `<script src>` 引入 | 双击即开，最省事 |
| B. 本地 HTTP 服务 | `python -m http.server` 后浏览器访问 | 需启服务 |

> **v5 现状**：以上两种都已移除。前端改由同源接口 `/api/price-data` 取数，不存在 `file://` 跨域问题；代价是必须跑 Node 进程（`npm run dev` / `node .output/server/index.mjs`），不能双击 HTML。

### 5.3 跨年日期处理

`date` 只有"月日"。补年份规则：取抓取日的年份；若抓取日在 1 月而数据日期在 12 月，年份减 1。边界情况记入日志人工核对。

### 5.4 涨跌幅口径

| 指标 | 公式 |
|---|---|
| 日环比 | (当日价 − 上一有效观测价) / 上一有效观测价 |
| 周环比 | (当日价 − 7 天前价) / 7 天前价 |
| 颜色 | 涨=红，跌=绿（中国习惯） |
| 缺失日 | 跳过取最近有效值，不补 0 |

## 7. 风险与对策

| 风险 | 影响 | 对策 |
|---|---|---|
| 私有接口变更/关闭 | 采集失败 | 日志告警 + 手动补抓；关键路径加字段校验 |
| 接口无历史 | 漏抓则丢数据 | 每日定时 + 失败重试 + 可手动补抓 |
| 日期无年份 | 跨年错乱 | 补年份规则 + 边界日志 |
| 0.00 占位 | 假价格污染曲线 | 入库前剔除 |
| 规格混淆 | 错误比价 | 曲线键用 standard_id 三元组 |
| 本机不开机 | 漏抓 | 可选切 GitHub Actions / 云服务 |
