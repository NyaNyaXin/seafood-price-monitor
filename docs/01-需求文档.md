## 1. 背景与目标

### 1.1 背景

前期调研确认：辽宁冻品水产批发价，公开可自动化的源极少。农业农村部 pfsc 辽宁无水产报送点；发改委中国价格信息网是零售价且半月更；真正可用的是**全国水产技术推广总站「智能渔技 / 水产时价云」**（`znyj.nftec.agri.cn`，官方 `.agri.cn` 域），它提供**日更的批发市场报价接口**，沈阳有 2 个报送市场。

但该平台**只有当日快照，不提供历史流水**。今天不存，明天就没了。因此需要一个「每天自动抓 → 自己存 → 看涨跌曲线」的系统。

### 1.2 目标

| 目标 | 说明 |
|---|---|
| G1 自动采集 | 每天定时抓取沈阳市 2 个水产市场的全部报价，无需人工 |
| G2 自主存储 | 数据落到本地数据库，逐日累积，形成自己的历史序列 |
| G3 涨跌可视化 | 按「市场+品种+规格」看价格曲线与涨跌幅 |
| G4 聚焦沈阳 | v1 只做沈阳（于洪、前当堡），架构预留扩展 |

### 1.3 非目标（v1 不做）

- 不做全国/全辽宁市场（架构预留，UI 先不开放）
- 不做微信公众号、抖音等社交源
- 不做采购决策/预测模型
- 不做多用户、登录、分享（个人单机使用）
- 不采集零售价（发改委源）

## 2. 数据源事实（已实测，非推测）

这些是写需求的事实基础，全部来自 2026-11-23 实测。

| 项 | 事实 |
|---|---|
| 平台 | 全国水产技术推广总站「智能渔技 / 水产时价云」`znyj.nftec.agri.cn:8089` |
| 接口 | `GET /API/Product/GetPriceNow` |
| 鉴权 | 免登录，公开 token `0000000000000000` |
| 分页 | 参数 `PageNum`（**大写 P**）+ `pageSize`，当日全国 1033 条 / 104 页 |
| 辽宁筛选 | `rid=4`（辽宁；注意 `rid=21` 是福建，不是辽宁） |
| 沈阳市场 | `unit_id=537` 辽宁省沈阳水产品批发市场（于洪，铁西洪湖二街17号）；`unit_id=538` 辽宁省前当堡鲜鱼批发市场（新民市） |
| 字段 | `product`(品种)、`product_id`、`standard`(规格)、`standard_id`、`unit`(市场名)、`unit_id`、`value`(价格字符串)、`date` |
| 日期格式 | `date` 形如 `11月23日`，**不带年份** —— 需在入库时用抓取日补全 |
| 数值异常 | 存在 `value=0.00` 的缺报占位，必须剔除；无负值、无非数字 |
| 当日规模 | 沈阳共 15 条（于洪 9 + 前当堡 6），全部有效 |
| 历史接口 | **无**公开的历史逐条流水接口；只有当日快照 + 品种均价统计（`GetPriceList`/`GetVolumeList`） |

> 结论：历史序列必须靠"每天抓、自己存"积累，这是本系统的核心价值。

## 3. 用户与使用场景

**用户**：单人（建辉），个人使用，本地或自有环境。

**核心场景**：
1. 每天固定时间自动跑一次采集（建议清晨，与早报节奏一致）。
2. 打开一个本地页面/看板，看到沈阳各市场、各品种的当日报价。
3. 点开某个品种，看过去 N 天的价格曲线和涨跌幅。
4. 能发现"某个规格突然涨/跌很多"的异常。

## 5. 数据规则（核心，防踩坑）

### 5.1 曲线的唯一标识

一条价格曲线 = **`unit_id` + `product_id` + `standard_id`** 三元组。

> 原因：同名"带鱼"在"冻 350≤条重＜500"和"统货"是两个规格，价格口径不同，不能混成一条曲线。必须用 `standard_id`（规格 ID）而非品种名做区分。这是本项目最容易出错的地方。

### 5.2 数据库表设计（逻辑）

```
price_obs（报价观测表）
  id            主键
  obs_date      数据日期 YYYY-MM-DD   ← date 补年份后
  fetch_time    抓取时间（ISO）
  market_id     unit_id  (537/538)
  market_name   unit
  product_id    product_id
  product_name  product
  spec_id       standard_id
  spec_name     standard
  price         数值（元/kg）
  UNIQUE(obs_date, market_id, product_id, spec_id)   ← 幂等键

fetch_log（抓取日志表）
  id, fetch_time, status, raw_count, kept_count, error_msg
```

### 5.3 清洗规则

| 场景 | 处理 |
|---|---|
| `value=0.00` | 剔除（缺报占位，不是真价格） |
| `date="11月23日"` | 用抓取年份补全 → `2026-11-23`；跨年需特殊处理 |
| 价格字符串 `"24.00"` | 转 float |
| 同一键重复抓 | UPSERT（覆盖或忽略），不新增行 |
| 某日某品种缺失 | 不插 0，曲线在前端断连 |

## 6. 非功能需求

| 类别 | 要求 |
|---|---|
| 可靠性 | 抓取失败重试 + 日志；数据入库幂等 |
| 性能 | 数据量极小（15 条/天，年约 5500 条），无性能瓶颈 |
| 可维护性 | 配置与代码分离（市场 ID、阈值、抓取时间可配）；单文件优先，减少依赖 |
| 可移植 | 本地单机可跑；架构不锁死在云服务，便于将来上线 |
| 成本 | v1 零外部成本（本地数据库 + 静态页面） |
